# AS2-W X + Piper X (`AS2W_PiperX`)

Single articulated robot that bolts the **Piper X** arm onto the **AS2-W X**
wheeled quadruped, using the same subtree naming as `../M20_Piper_own/` so the
control / teleop / RL code can address it with the usual body names
(`base_link`, `arm_base_link`, `arm_link1..6`, `gripper_base`, `gripper_link1/2`).

## Contents

| Path | What |
|---|---|
| `urdf/AS2W_PiperX.urdf` | Composed URDF: 28 links / 27 joints / 54 mesh references (27 unique STL files, ~41 MB) |
| `urdf/meshes/` | STL meshes copied from the two source packages (names kept as-is) |

## Provenance

* **AS2-W X**: official `as2w_description` package (`as2w.urdf`,
  `<robot name="AS2W">`, 18 STL meshes). Downloaded from
  <https://github.com/bgzou/log_tmp>, path
  `部署参考/Rob2Nav-as2w-backup/training/as2w-backup/as2w-current/assets/official-model/robots/as2w_description`.
  The package ships no `package.xml`, so the vendor field is unknown.
* **Piper X**: `piper_x_description` (`urdf/piper_x_description.urdf` + DAE/STL
  meshes, local copy under `own_assets/piper_isaac_sim/`).
* Generated by `scripts/tools/build_as2w_piperx_urdf.py` in the parent repo.
  Do not hand-edit the URDF: re-run the script instead.

## Assembly

`base_to_arm` is a fixed joint:

```
parent base_link  ->  child arm_base_link
xyz = (0, 0, 0.0798)   rpy = (0, 0, 0)
```

### Why the middle of the body

`base_link` (0.510 m long, x in [-0.175, 0.335]) has one continuous flat top
deck, measured with downward ray casts on a 15 mm grid:

| Surface | Extent | Height |
|---|---|---|
| Flat deck | x in [-0.12, +0.06], y in [-0.06, +0.06] | z = 0.076 |
| Rear bevel | x < -0.12 | drops to 0.032 |
| Side edges | |y| > 0.06 | slope down |
| Front sensor hood | x > 0.065 | rises to 0.135 at x = 0.335 |

Piper X works towards +x, so the arm is mounted at the middle of the wheelbase
(hip joints at x = +-0.2119) rather than on the rear deck: its whole workspace
stays in front of the robot, the 1.56 kg arm sits over the wheelbase centre
instead of cantilevered behind the rear axle, and the folded elbow overhangs
the rear by 0.11 m instead of 0.21 m.

With `xyz = (0, 0, 0.0798)` the 0.0985 m x 0.08 m plate spans x in
[-0.0585, +0.04]: fully on the flat deck, ~25 mm clear of the point where the
front hood starts to rise, and 3.8 mm above the deck (gasket/riser layer).

### Why yaw = 0 (Piper X faces forward)

At its zero pose Piper X folds the **elbow towards -x** and points the
**gripper towards +x**:

| Frame (zero pose, robot frame) | x | z |
|---|---|---|
| `arm_base_link` | 0.000 | 0.0798 |
| elbow (`arm_link3`) | -0.282 | 0.241 |
| `gripper_base` | +0.098 | 0.297 |
| finger tips (`gripper_link1`) | +0.232 | 0.309 |

So `rpy = (0, 0, 0)` keeps the hand pointing the same way as the robot's
sensors (front, +x), which is what the low-shelf pick-place task needs: the
robot approaches the shelf front-first and pitches the body down.

Flipping the arm by 180 deg (yaw = pi) would make the hand point backwards and
would swing the folded elbow over the front sensor hood - it is not used.

### Reach check (level body, body clearance >= 20 mm)

Random joint sampling (4000 poses, 83 % collision-free) gives, in the robot
frame:

| Height band | Max `gripper_base` x |
|---|---|
| z = 0.20..0.30 | +0.620 |
| z = 0.30..0.40 | +0.648 |
| z = 0.40..0.50 | +0.612 |
| z = 0.50..0.60 | +0.527 |

The nose is at x = +0.335, so the hand reaches ~0.31 m beyond the nose. Lower
pick points are reached by pitching the body down (already part of the task),
not by the arm alone: at `arm_joint2 ~ 1.2, arm_joint3 ~ -0.3` the upper arm
grazes the front hood.

## Naming

AS2-W keeps its original names (they are part of the AS2-W policy
correspondence): `base_link`, `FL/FR/RL/RR_hip|thigh|calf|foot` (the `*_foot`
joints are the continuous wheel joints), plus the fixed `JT128` lidar.

Piper X is renamed to the `M20_Piper_own` convention:

| Source | This asset |
|---|---|
| `base_link`, `Link1..6`, `Link7`, `Link8` | `arm_base_link`, `arm_link1..6`, `gripper_link1`, `gripper_link2` |
| - | `gripper_base` (fixed to `arm_link6`, carries the original Link6 gripper-base mesh) |
| `joint1..8` | `arm_joint1..6`, `gripper_joint1/2` |
| - | `base_to_arm` (fixed), `joint6_to_gripper_base` (fixed) |

Joint limits, axes, effort and velocity are copied unchanged from the Piper X
package; `gripper_joint1` is prismatic 0..0.05 m, `gripper_joint2` -0.05..0 m.

## Regenerate

```powershell
python scripts/tools/build_as2w_piperx_urdf.py `
  --as2w-urdf <path>/as2w_description/as2w.urdf `
  --piperx-urdf <path>/piper_x_description/urdf/piper_x_description.urdf `
  --mount-x 0 --mount-y 0 --mount-z 0.0798 --mount-yaw 0 --force
```

The script validates the result (single `base_link` root, unique link/joint
names, one parent per child, every mesh file present) before writing.

## Known limitations

* Only URDF + STL are committed. The USD is generated on first load by
  `DEEPROBOTICS_AS2W_PIPERX_CFG` (`UrdfFileCfg`, `fix_base=False`,
  `merge_fixed_joints=False`), cached in `usd/` next to this file.
  Run `python scripts/tools/zero_agent.py --task Visualize-AS2W-PiperX-v0`
  to view the robot standing still in Isaac Sim (pose + PD gains are documented in
  `docs/as2w_piperx_assembly_zh.md`, section 9).
* `arm_link6` has no visual/collision mesh: its original mesh (the gripper
  base) lives on `gripper_base`, exactly as in the M20 + Piper asset.
* Piper X leaves `Link7` with zero mass; this file sets 0.01 kg with a small
  inertia so the physics engine accepts it.
* The zero pose is the raw Piper X zero pose, where the folded elbow sticks out
  ~0.11 m behind the robot. For a cleaner parked pose use
  `arm_joint2 = 0.5, arm_joint3 = -0.5` (the `DEEPROBOTICS_M20_PIPER_CFG`
  initial pose), which keeps the elbow ~0.05 m behind the rear and the hand at
  (0.151, 0, 0.427).
